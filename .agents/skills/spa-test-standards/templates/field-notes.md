Append-only log of lessons learned from real sessions using this skill.
This file is how the skill gets "senior" over time: read it like it carries
the same authority as `SKILL.md`'s permanent sections — it just hasn't been
consolidated into them yet.

## Format
One bullet per lesson, most recent last:

```

```

Rules for adding an entry (see `SKILL.md` § Continuous learning loop for the
full procedure):
- Only record something **new, non-obvious, and reusable across any Convenia
  Vue SPA** — a flakiness root cause, a decision-rule edge case, a mock/selector
  gotcha, a correction about how testing should be done here. Not a one-off
  business-rule detail specific to a single feature.

  Keep the technique, drop the trivia.

## Log

- **2026-07-20** — A default `mockResolvedValue` (no `Once`) set in a shared `beforeEach`, combined with a `mockRejectedValueOnce` in one test for the error path, only overrides the *first* call after it's queued — later calls (or the same test if the mocked function runs more than once) silently fall back to the `beforeEach` success default. This can mask a real missing/broken error-handling path, and the symptom only appears when test execution order changes (e.g. in CI). Context: surfaced while reviewing a container test suite where an error-path test kept passing even after the error-handling code was accidentally removed, because a later call in the same test consumed the success default instead of the queued rejection. Related to the existing "Mock isolation between tests (Vitest)" rule — `vi.resetAllMocks()` in `beforeEach` avoids the queue/default interaction, but only if it runs before the per-test `beforeEach`/`it` re-establishes the default.
- **2026-07-20** — When Playwright's reporter flags several spec files as "slow", don't assume the slowest-looking file (most lines/tests) is the one with a real per-test cost problem: per-test runtime can be roughly uniform across the whole batch (e.g. ~15-20s/test) regardless of file size, meaning even the smallest flagged file is just as "slow per test" as the biggest — the actual problem is total serial runtime inside one worker, not a bloated test. Rule: split every flagged file by functional area (not by an arbitrary line-count threshold) so Playwright can spread the resulting files across more workers, even for a file that looks too small to bother with. Context: surfaced splitting a batch of 5 Playwright specs flagged as slow (ranging 3.7m-8.9m) — the smallest by line count and test count had the same average per-test time as the largest.
- **2026-07-28** — Running the unit-coverage command scoped to a single folder/file, then running the diff-coverage command directly afterward without regenerating the full merged report, makes diff coverage regress (a file that showed e.g. 50% missing one line can flip to 0% missing multiple lines) — the scoped run overwrites the merged coverage artifact with only that subset's data, discarding coverage the rest of the unit suite (and/or the separately-run integration suite) previously contributed to the same file. Rule: before trusting a `test:diff-coverage` result, regenerate coverage from the full unit run (and merge with integration coverage if that's part of the pipeline) rather than a path-scoped run — a scoped run is fine for iterating on a single new test's pass/fail, but not for judging the real diff-coverage percentage. Context: surfaced verifying a diff-coverage gap on one service file — a scoped rerun made the reported gap look larger than the true baseline until the full suite was re-run and merged.
- **2026-08-18** — Never hardcode an absolute future calendar date in a Playwright `getByLabel(...)` click on a date-picker day cell (e.g. `'quarta-feira, 12 de agosto de 2026'`) — it silently rots into a real failure once that date is in the past, especially when the field has a `minDate` restriction (past dates become disabled/unclickable, producing an infinite click-retry timeout that looks like an unrelated UI bug). Rule: compute the target date at runtime (e.g. "tomorrow") and format its label with the exact same formatter the component uses for its day-cell `aria-label` (commonly `Intl.DateTimeFormat(locale, { weekday: 'long', year: 'numeric', month: 'long', day: 'numeric' })` for calendars built on v-calendar), so the assertion never depends on when the suite happens to run. Context: surfaced in a "schedule a meeting" flow spec where a date picker had `minDate: new Date()`; the hardcoded label had already passed by the time the suite ran, and both tests using it failed with the same click-retry symptom.
- **2026-08-25** — To simulate a failed request in a test when that same endpoint is already mocked (success case) by the shared `beforeEach`/Page Object setup, prefer `page.unroute(<the exact same route pattern originally used to register it>)` and let it fall through to the suite's global catch-all (which returns a 500 for any unmocked request matched against the tracked API list) instead of re-registering a competing `page.route(...).fulfill({status:500})` on top. This only works cleanly when the endpoint is only ever called with one HTTP method through that URL pattern; if the same path is shared by multiple methods (e.g. GET list + DELETE item), unroute still removes ALL handlers for it, so re-add a method-filtered `page.route` with `route.fallback()` for the other methods instead of leaving it fully unmocked. Context: surfaced in review feedback asking to avoid "touching the Playwright route API directly" in error-path tests that had to override an already-mocked GET endpoint.
- **2026-08-31** — When creating a new spec or helper file (not just when moving/renaming one), import project modules (setup/fixtures, page objects, other helpers) using the project's absolute path alias (e.g. `@tests/specs/<Feature>/...`) from the start, not a relative path (`../setup`, `../helpers/X`) — a relative import works fine locally, but code review flags it and asks for the alias, since it's more robust to future file moves and consistent with the rest of the suite. Context: surfaced in review feedback on a freshly split spec file and its newly extracted helper, both created with relative imports from the outset, not introduced later by a move.
- **2026-09-03** — Don't accept a PR's test waiver claiming "no test harness available" for an error/edge branch at face value. Check whether a sibling module in the same domain (same store family, same service layer) already has a real unit-test harness covering the equivalent pattern; if one exists, the waiver is invalid. Context: a PR waived a generic-error-branch test citing no harness, while a sibling store module in the same feature already had dozens of passing unit tests exercising the identical dispatch/mutation pattern.
- **2026-09-03** — When a PR changes the signature of an already-tested function/action (e.g. adds a new required parameter), check the existing test file covering it was updated to match. A diff that only adds new tests can leave the old suite exercising a stale call shape, silently losing real coverage. Context: a PR added a parameter to an existing store action; the action's existing test file was untouched and kept invoking the old signature.
- **2026-09-03** — Before writing or waiving a unit test for a new Vuex action's error branch, verify the action actually implements the project's error-exposure contract (dispatches a visible failure/flag on error). An untested branch may be untested because the implementation silently swallows the failure — a correctness bug the missing test would have caught. Context: one of several new sibling actions in the same file didn't dispatch the error-feedback pattern the others did, and its test waiver hid a real silent-failure bug.
- **2026-09-03** — When adding a new employee/user fixture to a mock list for an action that resolves an entity in two steps (e.g. a GraphQL "get full record" call followed by a companion REST id-lookup call translating an external uuid to an internal id), mock BOTH steps for the new entity, not just the primary one. If the second step's mock is missing, the action's early-return-on-failure logic swallows the error silently and leaves the store holding stale data from a previous fetch — no error surfaces, and the symptom looks like a rendering/logic bug (wrong name/content shown) rather than a missing mock. Context: added a new employee to a GetEmployee GraphQL fixture but forgot the paired `api/v1/companies/.../employees/uuid/<id>` REST mock; a Playwright test failed with the UI showing the previous employee's data instead of an error, and the root cause was only found by tracing the two-step fetch action's early return.
- **2026-09-14** — When a component has two sibling elements controlled by mutually exclusive theme classes (e.g. `.-theme-a { display: none }` outside the theme, `.-default { display: none }` inside it), merging both into a single element carrying both classes silently hides it in every theme — and a snapshot test that only covers the collapsed/empty state (`v-if` false) won't catch the regression, since the rendered content only diverges once the conditional element actually renders. Rule: when testing theme-alternated elements, always mount with the state that makes them visible and count/inspect the rendered nodes, rather than trusting only the default-state snapshot. Context: surfaced after a template merge collapsed two theme-specific buttons into one with both classes, making the button invisible in both themes; only a mount with a truthy prop value exposed the missing/duplicated node.
- **2026-09-17** — When asserting compiled CSS via a `findCompiledCssRules`-style helper (real CSSOM walk) on a base selector that a SCSS `@extend` targets, don't destructure the first match (`const [rule] = findCompiledCssRules(SELECTOR)`) — `@extend` makes the compiler emit multiple separate CSS rules sharing the exact same `selectorText` (one from the extended placeholder's own rule, another from the component's direct declaration block), and the property you're checking may not be in the first one returned. Rule: use `.some((rule) => rule.includes(...))` across all matched rules instead, the same pattern already used to assert a property's *absence*. Context: surfaced adding a test for a `box-shadow` declared directly on a component root that also `@extend`s a shared placeholder — destructuring `rules[0]` grabbed the placeholder-derived rule (which didn't contain `box-shadow`) and failed even though the property was correctly compiled into the other rule.
- **2026-09-21** — When writing a new failure-path Playwright test by copying the override pattern from an existing sibling test in the same file, still validate that pattern against this skill's own guidance before reusing it — pre-existing test code can itself already be off-standard, and copying it silently propagates the anti-pattern to the new test. Concretely: a hand-written `page.route(sameGlob, ...).fulfill({status:500})` re-registered after `page.unroute(sameGlob)` was copied into a new test from two older sibling tests that did the same; per the existing "simulate a failed request" note, a bare `page.unroute(sameGlob)` alone (relying on the suite's global 500 catch-all) was sufficient since the failing method didn't share its route glob with another method that same test exercised — all three tests (old and new) were simplified once this was checked. Context: surfaced when the user flagged the newly added test's hand-rolled `page.route().fulfill()` as off-standard; the two sibling tests it was copied from had carried the same avoidable pattern unnoticed.
- **2026-09-29** — Ao testar um recurso que trava/desabilita células (lock por regra), a fixture precisa deixar pelo menos uma célula editável e não-controle na mesma linha travada, e ter uma segunda linha sem a trava; um preset em que toda a linha trava só cobre o estado inicial, e a lógica de edição/recálculo e o isolamento por linha ficam sem teste sem ninguém perceber. Context: os testes de integração de uma trava de peso por linha usavam uma avaliação com 2 papéis em que ambos ficavam desabilitados; trocar os tipos por linha do handler de edição pelos globais não quebrava nenhum teste.
- **2026-09-30** — Never write unit tests for service modules: services are already exercised by the integration tests (Playwright runs the real service code against the mocked endpoints), so a service unit test only duplicates coverage — this holds even for services with internal pagination loops or payload mapping. Store (Vuex/Pinia) code gets unit tests only when it carries real logic (conditional branches, data transformation/merge, chaining of dispatches/services); pass-through mutations/actions/getters are not tested, and a module with no logic gets no test file. In review/coverage-gate mode, flag new service or pass-through store unit tests as unnecessary and close any coverage gap through the integration flow instead. Context: a correction from the user on how testing is done here; already folded into SKILL.md's decision rule, templates table and coverage gate, plus unit-store-vuex.md, and the service unit template was removed.
- **2026-10-02** — Quando quase todos os specs de um arquivo falham localmente no primeiro `expect(...).toBeVisible()`, inclusive testes não tocados e rodando com `--workers=1`, verifique o `TEST_EXPECT_TIMEOUT` do `.env` antes de investigar o código: um timeout local curto (~5s) não cobre a compilação sob demanda do Vite dev server. Rode com `TEST_EXPECT_TIMEOUT=30000` (valor do CI container) para separar ambiente de regressão. Context: o mesmo teste falhava em HEAD sem nenhuma mudança local e passava com o timeout maior.
- **2026-10-02** — Quando uma migração passa a entregar um dado por outro endpoint (ex.: campos antes vindos de uma query separada agora embutidos no payload principal), adicionar o dado na fixture não basta: algum spec precisa conferir esse valor na tela. Sem isso, a fixture nova só dá falsa confiança, e remover o campo do objeto montado pelo container não quebra nenhum teste. Context: a fixture do detalhe ganhou respostas de perguntas, mas nenhum spec conferia esse texto.
- **2026-10-02** — Quando um teste dispara duas ações seguidas que exibem feedback (ex.: criar e depois editar), o CFeedbacks mantém o card antigo no DOM durante a transição de saída com o mesmo testid `feedback-<type>-0`, causando strict mode violation. Valide o 1º feedback, feche-o pelo botão e espere `expect(getByTestId(/^feedback-/)).toHaveCount(0)` antes da próxima ação. Nunca use timeout.
- **2026-10-05** — `locator.isVisible()` não espera: um `if (await input.isVisible()) await input.fill(...)` antes de confirmar um modal carregado via `defineAsyncComponent` pula o preenchimento quando o chunk ainda não carregou, e o botão de confirmar fica desabilitado até estourar o tempo ("element is not enabled"). Quando o cenário sempre mostra o campo, preencha direto (`fill` já faz auto-wait); se o campo for de fato condicional, faça um cenário pra cada variante em vez de decidir em tempo de execução. Context: dois testes de exclusão falhavam em ~10% das execuções repetidas, sempre nesse ponto, e o flaky foi atribuído aos mocks.
- **2026-10-05** — As rotas do Mirage valem pra todos os specs (o server sobe em toda carga de página com `VITE_USE_MOCK=true`, mesmo sem bootstrap) e interceptam o XHR antes de qualquer `page.route`. Ao migrar mocks pro Mirage, leve só os endpoints exclusivos da feature (confira com grep nos services de outras features); endpoints compartilhados, como listas de processos de assinatura usadas por várias categorias de documento, ficam em `mockFromList`. Como o Mirage não gera eventos de rede no Playwright, contadores de request via `page.route` viram asserções sobre `window.__mockServer.db` (registro salvo/alterado, quantidade de registros relacionados). Context: migração dos mocks REST de uma tela de documentos que também consumia endpoints de assinatura compartilhados com outras telas.
- **2026-10-06** — Antes de investigar um `test.skip`, rode o teste sem o skip: a causa pode ter sido corrigida em outro PR (ex.: fixture ajustada) sem ninguém reabilitar o teste. Para achar endpoint REST sem mock, escute `page.on('request')` no carregamento: rotas do Mirage não geram evento de rede, então qualquer request que apareça para o host da API está sem mock e vai para a rede real, onde o `if (!err)` do store esconde a falha. Context: dois testes pulados por "falta de mock" já passavam após uma correção de fixture feita em outro PR; o endpoint sem mock só apareceu escutando as requests da página.
- **2026-10-07** — No Vitest com jsdom, File/Blob não tem `arrayBuffer()`; código que chama `file.arrayBuffer()` dentro de try/catch cai silenciosamente no fallback, e o teste parece cobrir o caminho principal sem cobrir. Leia arquivos via `FileReader` (já suportado pelo jsdom) ou confirme com um `toHaveBeenCalled` do passo seguinte. Context: um teste de validação de upload passava pelo catch e o mock da validação nunca era chamado.
- **2026-10-09** — Quando a função testada compara com um valor que vem do back (ex.: tipo de pergunta `'Texto'`), use o literal no teste, não a mesma constante que a implementação importa: se a constante mudar para um valor errado, teste e código mudam juntos e o teste continua verde. Constantes de enum interno (mesma fonte para UI e lógica) podem continuar compartilhadas. Context: um teste de mapper de payload passava com a constante do tipo alterada para um valor que o back nunca envia; só falhou depois de trocar a constante pelo literal no teste.
- **2026-10-13** — Corrida de ordem de carregamento (ex.: container ou action decide o fluxo com base em permissões que o App ainda está buscando) se testa na camada unitária, não no Playwright: os mocks respondem rápido demais para reproduzir a corrida, e segurar a resposta com um `page.route` manual que conta requisições foge do padrão `mockFromList` e amarra o teste à implementação (se a chamada em andamento passar a ser reaproveitada, o gate nunca libera e o teste trava até o timeout). Teste o método/action sem mount, com mocks que só atualizam o estado depois de um `await Promise.resolve()`; mocks síncronos não pegam a remoção do `await`. Confira tirando o `await` do código. A integração fica só com `mockFromList`, conferindo o comportamento com a página estável. Context: um helper de Playwright com gate por contagem de requests foi recusado no review e substituído por testes unitários do container e da action.
- **2026-10-15** — `hasFeedback({ index: N })` com N > 0 só funciona se os feedbacks anteriores ainda estiverem na tela, e eles somem sozinhos depois de ~5s (delay do CFeedbacks), enquanto o testid usa a posição na lista. Se o feedback anterior for um erro vindo de request sem mock, o teste passa local (rápido) e falha em todas as tentativas no CI (lento). Antes de usar index > 0, confira de onde vêm os feedbacks anteriores: mocke o request e use index 0. Context: um teste de calibração esperava sucesso no índice 1 por causa de um erro de um POST sem mock no carregamento.
- **2026-10-15** — `expect(page).toHaveTitle(destino)` logo depois de um clique de navegação passa por um instante mesmo quando a página de destino falha num request sem mock e redireciona de volta: o título muda antes do loader do destino terminar. Localmente o polling pega esse título passageiro e o teste passa; no CI lento, o redirect acontece antes do polling e o teste falha. Mocke os requests do loader do destino e confira um conteúdo que só aparece depois que ele carrega (ex.: campo preenchido com o valor da fixture), não só título/URL. Context: um teste de "abrir edição pela listagem" era flaky no CI porque o GET do detalhe não tinha mock e o formulário voltava para a listagem com feedback de erro.
- **2026-10-15** — Popover com `hide-on-scroll` (ex.: ações de item em MultiSelectWithPopover → CPopover) pode fechar sozinho logo depois de abrir: o `click()` do Playwright rola o alvo até ficar visível dentro de um container rolável (ex.: modal fullscreen) no mesmo passo do clique, e o evento de scroll chega no frame seguinte, com o popover já aberto. O próximo `waitFor`/`expect` espera até o timeout (90s x retries no CI). Chame `scrollIntoViewIfNeeded()` no alvo antes do `click()` para o scroll terminar antes da abertura. Rode localmente sem `VITE_INTEGRATION_TEST`: hoje o CI também não tem essa variável, então o guard de scroll do CPopover fica desligado nos dois.
- **2026-10-16** — Com `fullyParallel: true` no playwright.config, o Playwright distribui testes (não arquivos) entre workers e shards, então dividir um spec lento não reduz o tempo total, nem local nem no CI. Divida por organização (telas distintas, mais de ~400 linhas). Para ganhar tempo, reduza navegações: funda testes cujo setup e entrada são iguais e cujas asserções são um subconjunto de outro teste (ex.: 'lista a aba X' dentro de 'troca para a aba X'; 'cancelar' antes de 'confirmar' no mesmo modal). Context: um spec de 1267 linhas dividido em 5 arquivos rodou no mesmo tempo por teste; só as fusões reduziram navegações.
- **2026-10-16** — Um `locator.waitFor({ timeout: N })` com timeout fixo no Page Object substitui o `expect.timeout` do config. Quando N é menor que o timeout do CI container (ex.: 15s contra 30s), o teste passa local e estoura no CI lento, inclusive nos retries, e todos os specs que usam o método herdam o flaky. Use `await expect(locator).toBeVisible()` sem timeout explícito. Context: testes de detalhe falhavam no CI sempre no waitFor de 15s do método de navegação compartilhado, com o expect.timeout do CI em 30s.
- **2026-10-16** — Componentes com elementos alternados por tema (ex.: dois botões .cancel no CSearchBox, um com display:none) fazem um seletor CSS por classe casar 2 nós e cair em strict mode violation. Use getByRole/getByTestId, que ignoram elementos ocultos, em vez de .locator('.classe').
- **2026-10-16** — Seletor `getByRole('link', { name: <título da página> })` casa com o título do header do layout e também com o item ativo do menu lateral; dependendo do estado da sidebar (colapsada/visível) dá strict mode violation de forma intermitente. Use `getByTestId('header-title')` + `toHaveText(título)`.
- **2026-10-19** — Componentes funcionais do @convenia/components (ex.: CTypo, `functional: true`) descartam atributos e diretivas passados neles: `data-testid` e `v-tooltip` colocados direto no componente nunca chegam ao DOM, e o `getByTestId` espera até o timeout. Coloque testid e diretivas num elemento nativo em volta (span/div). Antes de culpar o mock, confira `functional` no componente. Context: um testid num CTypo não era encontrado, enquanto o getByText do mesmo texto passava.
- **2026-10-19** — Numa migração incremental para o Mirage, quando outros specs ainda mockam os mesmos endpoints via page.route, não registre a rota com passthrough por predicado. Faça o gate no registro: `if (!hasMockBootstrap('<feature>')) return` no início do routes da feature. Sem seed, as rotas não existem e o passthrough global '**/**' deixa a request seguir para o page.route. Monte os paths das rotas com as funções de `services/names.js` usadas pelos services, sem repetir as strings. Context: o review recusou um passthrough por regex + flag window para manter os specs antigos funcionando.
- **2026-10-20** — Componente com o mixin MediaQuery (@convenia/mixins) usa inject de getIsXsMobile/getIsMobile/getIsTablet/getIsSafari/getIsIOS; no shallowMount, sem `provide` dessas funções, o render quebra com 'this.getIsMobile is not a function'. Passe `provide` com todas as cinco (não só a usada no template) pra evitar os warnings de injection.
- **2026-10-21** — Após erro de back que vira mensagem de campo num CFormBuilder, chame onValidate só depois de um nextTick: o ValidationProvider ignora campos com disabled e o form ainda está desabilitado (isSubmitting) no mesmo tick; specs que clicam em Salvar de novo para ver a mensagem mascaram o bug.
- **2026-10-21** — Fallback `try { expect(...).toBeVisible({ timeout: 5000 }) } catch { page.reload(); expect(...).toBeVisible({ timeout: 20000 }) }` num método de navegação do Page Object piora o flaky em vez de corrigir: no CI lento o primeiro load passa dos 5s, o reload joga fora o progresso e recomeça do zero com um teto menor que o expect.timeout do CI. Use só `await expect(locator).toBeVisible()`. Para conferir localmente, rode com `taskset -c 0` + `CODE_COVERAGE=true` + `--workers=2` contra o build de CI (`CODE_COVERAGE=1 yarn build` + `vite preview`).
- **2026-10-23** — Teste de erro com `mockFromList` passa mesmo quando a fixture não casa: request sem definição (payload diferente, data dinâmica, rota sem mock) vira 500 genérico e o feedback de erro aparece do mesmo jeito. Para validar, troque o `statusCode` da fixture de erro para 2xx e confirme que o teste falha; e use dados fixos (nunca `dayjs()` de hoje) quando o `postData` entra na fixture. Context: dois testes de erro antigos passavam pelo 500 genérico (data de hoje no formulário; redirect para uma tela sem mock), não pela fixture de erro.
- **2026-10-23** — Path de fixture com colchetes na query (ex.: `departmentIds[]=id`) não casa no glob do Playwright, que lê `[]` como classe de caracteres; escape com `\\[\\]` no JSON. Confira a URL real com `page.on('request')` antes de culpar o mock. Context: troca de um `page.route` por regex por fixture `mockFromList`; a URL real também tinha o tipo no plural, que o regex antigo casava só pelo prefixo.
- **2026-10-23** — O CButton descarta cliques por 500 ms depois de um clique (debounce interno, classe `-clicked`). Teste que clica duas vezes no mesmo botão (ex.: enviar vazio para ver a validação e enviar de novo depois do `fill`) perde o segundo clique quando os passos são rápidos, e o request nunca sai. Antes do segundo clique, espere `expect(button).not.toHaveClass(/-clicked/)`; nunca `waitForTimeout`. Para reproduzir, rode com `taskset -c 0`. Context: um teste de criar comentário falhava no CI depois de trocar um `waitForTimeout(300)` por uma asserção de valor; o trace mostrou o botão com `-clicked` e nenhum POST.
- **2026-10-29** — Polling com setTimeout agendado depois de um await: clearTimeout no onBeforeUnmount não basta, pois se a etapa desmonta com a requisição pendente o próximo timeout é agendado depois da limpeza. Teste na camada unitária: mock da action retornando uma promise deferida, destroy() antes de resolver, depois vi.advanceTimersByTimeAsync e confira a contagem de chamadas. Inclua um caso de controle mostrando que o polling continua com o componente montado.
- **2026-11-03** — No @vue/test-utils v1 (Vue 2), scopedSlots como string template com subárvore 100% estática quebra com 'Cannot read properties of undefined (reading staticRenderFns)'; adicione um bind dinâmico (ex.: `:data-label="props.label"`) no elemento externo e em cada elemento com filhos estáticos. E o `trigger('click')` do VTU ignora elementos disabled: para testar clique num controle disabled, use `element.dispatchEvent(new MouseEvent('click', { bubbles: true }))`. Context: testes de slot com controles de formulário num componente de radio, rodando em Vue 2 e Vue 3.
- **2026-11-03** — Num componente `<script setup>` com `defineExpose`, o `wrapper.vm` do vue-test-utils-compat (harness Vue 3 da biblioteca) não traz o método exposto (`wrapper.vm.toggle is not a function`), embora o Vue 2.7 traga. Para um teste que roda nos dois, monte um pai com `template: '<c-x ref="x" v-bind="props" />'` e chame `wrapper.vm.$refs.x.metodo()`, que é como o componente é usado de verdade. Quando o bug é um `click-outside` fechando algo sozinho, o teste de regressão é registrar um listener de `click` no `document` (com `attachTo: document.body`) e conferir `not.toHaveBeenCalled()` depois da interação. Confira emitted antes do `wrapper.destroy()`: no Vue 3 o unmount limpa o `emitted()`. Context: troca de um `$el.click()` sintético por um método exposto via `defineExpose`; o clique sintético chegava ao `document` e fechava o date picker que estava no slot.

Antes de confiar no número, confira também que `yarn test:coverage` terminou sem falhas: com teste vermelho ele não reescreve o cobertura-coverage.xml e o diff-coverage lê o relatório antigo.
- **2026-11-04** — In MirageJS, `schema.db.<collection>.find()` only accepts an id (or a list of ids), not a predicate: `find(fn)` returns null without any error, so a 'duplicate name → 422' check never fires and the route returns 200. Use `where(fn)[0]` (or `findBy({...})`) to search by field.
